# The secure origin

**The governing fact: the secure origin is exactly as safe as the least trusted thing it serves.** It exists so that a credential typed into it can't be read by card code. The browser's same-origin policy does the isolating: the app page, and every card evaluated in it, can't read another origin's document, keystrokes or form values. That guarantee is about the _origin_, not the page. One script served anywhere on the origin, from any path, can read every window open on it. So the origin serves the pages `packages/secure-origin` builds — the shell, and the credential fields the app frames — and nothing else. No realm, card module, realm asset, host app bundle or third-party script, ever.

## What it serves

- **The shell**, at the path of the configured URL (`/` deployed, `/secure` in development): the built `index.html`, with no inline script, the files it loads (its entry point `shell.js`; the chunks that imports, among them `shared.js` with Ember and the components both entries use, the shell's own components staying in `shell.js`; `layers.css`, the order of the pages' cascade layers, which the build links ahead of every other stylesheet; and the components' stylesheets, `shell.css` among them with `global.css`'s page-wide rules: boxel-ui's reset, the typeface and the page's background), and boxel-ui's `variables.css`, `theme.css` and the app's typeface, read from boxel-ui as they are. `createSecureOrigin` builds a `routes` table of every path served, from the build's manifest (see below).
- **Pages** each have a path of their own beneath the shell's address, and every page is the same shell document with the same headers. `src/shell/pages.js` lists the paths (`PAGE_PATHS`). It is plain values, so the realm server imports it and serves the shell at exactly those paths. The shell's router (`src/shell/app.gts`) has a route for each, written out by hand and kept in step: the policy test fails when a page in the list isn't loaded, or doesn't draw what only it draws. A new page means an entry there, a route and its template in `app.gts`, an entry in the policy test's `SHELL_PAGES`, and nothing on the server. The pages are `sign-in`, `cli-sign-in` (`boxel keys sign-in`) and `cli-auth` (`boxel profile add`, which hands the CLI a Matrix login token; see the `secure-session` skill) (components in `src/shell/sign-in/`), `register` and `verify-email`, where a registration email's link lands (`src/shell/register/`), `forgot-password` and `reset-password`, where a reset email's link lands (`src/shell/password-reset/`), and `google-callback`, where Google returns. `sign-out` ends the window's session and moves on to `sign-in` as a route transition, keeping the app page in its `#return=` (when listed) as the one the next sign-in hands back to; it never goes back to the app first. The key pages are `keys` (the user's keys: list, add, replace, delete), which the shell's own address also shows, with `keys/add` and `keys/<key id>/share` beneath it, `enter-key`, `replace-key`, `share-key` and `swap-key` for a window opened for something, `approve` and `review-changes` for approving a card's requests as one batch, `keys/<key id>/use` for setting a key up for a card from the key page, and `connect` and `connected` for signing in through an OAuth client (components in `src/shell/keys/`; see "The key pages" below). A key id is the only value a path carries. Anything else a page is told rides in its query string (plain values, such as the CLI's `port` and `state`) or its fragment (anything that names an origin or a URL, and anything secret). `pageURL` in `src/shell/urls.js` builds a page's address, and the host (`lib/secure-sign-in.ts`) and the CLI (`secureOriginPageUrl` in `src/lib/sso-login.ts`) build theirs the same way. A sign-in the app started carries `#return=` too, and the window hands it back with a login token (the `secure-session` skill); `return` is honoured only on an origin in the shell's `boxel-app-origins` markup, which the realm server fills with the credential fields' app origins.
- **Addresses that name a page by `?mode=`** keep working. Earlier CLI releases and emails already sent use them, so they must not break. Before the app starts, `shell.js` rewrites such an address to the page of the same name (`LEGACY_MODES` in `pages.js`), keeping the rest of its query string and its fragment; `enter-key` with `then=keys` is `keys/add`. A `mode` that names no page renders nothing.
- **Moving between pages.** Every move a page makes goes through `navigation` (`src/shell/navigation.js`), so a component test sees where it would have gone. Once the router runs, a move to another page whose address is a path alone is a route transition, so the browser's back button returns to the page before (the key page and the pages beneath it move this way). An address with a query string or a fragment, or one off the shell, loads as a new document, because a page reads what it is told as it starts. `navigation.back(url)` goes back to the page an in-app move came from, or, for a page loaded at its own address, on to `url` in its place.
- **The trail of key pages.** `KeysWindow` draws, on the purple above the panel, breadcrumbs of the key pages the window came through to reach the one shown (Pret UI's `Breadcrumb` over `trail.ts`, wrapping onto more lines in a narrow window), so a user who moves on from the page the window was opened on can go back to it, or to any page between, as it was opened. A key page that sends the window on to another page with something in its fragment builds the address with `withWayBack`, which puts its own address (path and fragment) in the next page's fragment as `back`: Approve's "Add a new key", Replace key's Reconnect, Share key's and Swap key's "Go to your keys", Use with card's approve, and from the key page Reconnect, Approve for a card and a limit notice's usage link, and the limits page's Approve for a card. That address carries its own `back`, so the whole trail is read from the address. A page beneath `keys/`, and the connect page reached from the key page's Connect an account, has the key page above it; a route transition keeps no fragment, so that key page is the address the document was loaded at, as it was (`documentAddress()` in `navigation.js`, which the router records as the app boots and a component test sets with `noteDocumentAddress`). A crumb loads its page's address again (`goBackTo`, through the `Breadcrumb`'s `@onSelect`, which takes the click over from the link), so nothing is saved or changed on the way. The one exception is the page the document was loaded at, just above a page a route transition reached from it: that crumb goes back through `navigation.back`, as the browser's back button does. A page's own way back to the key page (Cancel, "Back to your keys", done) goes to `keyPageURL()`, the nearest key page above it in its trail as it was, so it keeps that key page's own trail as its crumb does. `back` names only a key page (one `pageTitle` names); anything else, a sign-in or sign-out page among them, ends the trail. Each page's heading is its title from `pageTitle` in `trail.ts`, the same short name its crumb shows ("Your keys", "Add key", "Approve", "Swap key"), so the heading and the last crumb always match; a page's situational wording goes in its intro. Outcome states (done, needs-admin, not the owner) keep their own headings.

- **The pages are Boxel's sign-in screens**, the only place a user signs in, creates an account or resets a password (ADR 005 §1.7), and every one is a Glimmer component. `src/components/` holds AuthContainer, AuthButton, AuthFormField (Pret UI's Field, its label above the control; its block is given the label's id and the id its control takes) and AuthHeading (a screen's title, an `h1`, or an `h2` under a page that heads itself) and ports of the boxel-ui components they use that haven't moved to Pret UI yet (Button and the icons), each with boxel-ui's scoped CSS. A page that waits shows Pret UI's Spinner (BusyMessage, shared with the app's own loading page so a redirect keeps the same indicator; Button's `@loading`; the account-setup wait), and a field that is right says so with Pret UI's Cue in the success tone. Every text field, password field, textarea and the username's input group is Pret UI's Input, Textarea or InputGroup. AuthContainer sets Pret UI's field knobs (`--pretui-field-h` to `--boxel-form-control-height`, `--pretui-field-font-size` to `--boxel-font-size-sm`), so the sign-in screens' fields are the app's full size beside AuthButton; the key pages keep Pret UI's compact field. A password field is Input with `@type='password'`, not PasswordInput, which puts the attributes it is given on its wrapper rather than its input (a password manager reads `name` and `autocomplete` there) and reaches Pret UI's strength estimator. `src/screens/` holds the screens themselves, presentational and stateless: sign-in, the registration steps and the password-reset steps, each taking its values and actions as arguments and its password fields as a block. The host may import from the package (its signed-out landing uses AuthContainer), and the package never imports from the host. On the secure origin, `src/shell/sign-in/` holds the sign-in form's controller, the CLI sign-in, the Google callback and the pages a sign-in ends on; `src/shell/register/` and `src/shell/password-reset/` hold account creation and password reset, and render those screens with the package's own inputs. The decisions behind them are plain modules: the CLI's loopback target and hand-off (`src/security/cli-handoff.js`), the registration's stages and the new account's first sign-in (`src/security/registration.ts`), and the reset link (`src/shell/password-reset/reset-link.ts`). The icon components copy boxel-ui's paths for the logo, Google's "G", and the check mark. The CLI sign-in page (`src/shell/sign-in/cli-auth-page.gts`) renders the sign-in screen too, naming themselves with the screen's `@title` and saying what signing in grants the CLI in its `intro` block, whose type and spacing the screen sets. Each screen's controls carry two sets of test attributes (`data-test-login-btn` beside `data-test-secure-password-submit`, and so on), and specs select by either, so keep both when editing one.

- **The credential fields**, at `credentials` beneath the shell's path: the built `credentials.html` and the files it loads (its entry point `credentials.js` and `credentials.css`; the chunks it shares with the shell, `shared.js` and `shared.css`; `layers.css`; and `session.js`, imported to set a new password through the realm server), and the shell's typeface. See below.

Adding a screen means adding it to `packages/secure-origin`, as [ADR 019](../../../docs/adr/019-build-the-secure-origins-pages-as-their-own-ember-app-on-pret-ui.md) sets out. Each addition must be code this repo owns and reviews. Never add a proxy, a passthrough to realm routing, a CDN script, an analytics snippet or a host-app import.

The pages are deliberately not host components. ADR 019 records why: everything the origin serves is trusted code, so it is built from a package of its own, behind an import allowlist, with a reviewed record of what it ships.

**Draw the pages with Pret UI.** A page uses Pret UI's component, helper or modifier wherever one does the job and can ship on the origin, and boxel-icons for icons (ADR 019 §1.11). Never add a component, helper, modifier or icon of the package's own for a job Pret UI or boxel-icons already does. A Pret UI module can ship when everything it reaches passes the import allowlist (§1.3) and it runs under the policy (§1.5). Pret UI is allowed as a whole, boxel-ui included where Pret UI reaches it, but the package never imports boxel-ui itself. The allowlist stays a committed list of package names: ADR 019 §1.3 names the packages it reviewed, and any other one, including a new dependency of boxel-ui or Pret UI, joins the list only in a change reviewed for it. The usual reasons a module can't ship are a bound `style` attribute in its template or in a boxel-ui component it renders, a `<style>` element added at run time or left unscoped, and an import of the base realm; fix those in Pret UI, not with a copy here. `node scripts/adr-for.mts <path>` lists the package's own components still waiting to move.

## How the pages are built

`packages/secure-origin` is an Ember app built with Vite and Embroider. Templates are compiled at build time, and the build holds no runtime template compiler. It has two entry documents, `index.html` (the shell) and `credentials.html` (the credential fields). The pages' own modules are in `src/shell/` and `src/credentials/`. The security logic — the credential frame's protocol and forms, the Matrix requests, session handling, origin matching and response redaction — is in `src/security/`, which imports nothing from Ember, Glimmer, Pret UI, boxel-icons or the pages (a `no-restricted-imports` rule enforces it).

- **Pret UI, boxel-ui and boxel-icons, the way the host reads them.** Pret UI's and boxel-ui's package exports point at their `.gts` source, so the build compiles them from source, as the host's Vite build does: their templates at build time, their `<style scoped>` into the build's stylesheets, and boxel-ui's tasks through `ember-concurrency`'s async-arrow transform, as boxel-ui's own build and the host's run it. The package depends on Pret UI and boxel-icons, never on boxel-ui, which reaches the pages only through Pret UI. boxel-icons exports only its own build (`dist/`), so `pnpm build` (and `lint:build` and `test:components`) first runs `build/ensure-icons.ts`, which builds boxel-icons' JavaScript when it has no build or a source is newer than it, and keeps a build already in place (the realm-server image's boxel-icons stage, CI's restored builds). So every site that builds the origin builds boxel-icons first.
- **Two builds in one.** The production `vite build` runs two Vite environments: `client`, the pages the origin serves, written to `dist/`, and `probe`, the build probe, written to `dist/probe/` with a manifest of its own. The probe (`probe.html`, `src/probe/`) is a page no user is sent to and the realm server never reads or serves: it renders a Pret UI component that wraps boxel-ui (Accordion) and a boxel-icons icon, so the allowlist, the build record and the policy test cover what those packages ship before any real page uses them. It is a build of its own so the modules it shares with a page never move that page's modules into another chunk. The component tests' development build has no environments and no probe. A scratch build for screenshots (`vite build --outDir <scratch>`) writes the pages to `<scratch>` and the probe to `<scratch>/probe`; run `node build/ensure-icons.ts` first in a fresh checkout. It rewrites `build-record.json` too (see the build record below).
- **The import allowlist.** `build/import-allowlist.ts` fails the build when its output holds a module from anywhere but the package and the packages its `ALLOWED_PACKAGES` names, naming the module and its package, or any module of Ember's runtime template compiler. It reads the bundle, so it sees a module reached through a dependency's own imports. The list is written by hand, never computed from the lockfile: it names Ember, Glimmer and the build's runtime helpers, and the packages [ADR 019](../../../docs/adr/019-build-the-secure-origins-pages-as-their-own-ember-app-on-pret-ui.md) §1.3 reviews that the build actually reaches (Pret UI, boxel-ui, boxel-icons, and those of boxel-ui's run-time dependencies the shipped components import). boxel-ui's `package.json` declares only its stylesheets and its own tests as side effects (`"sideEffects": ["**/*.css", "./tests/**"]`), so a Pret UI wrapper of a boxel-ui component brings in that component's own imports rather than everything boxel-ui's `components` index re-exports. A page that starts using a component whose imports reach another package adds it to the list in the same change, reviewed as [ADR 019](../../../docs/adr/019-build-the-secure-origins-pages-as-their-own-ember-app-on-pret-ui.md) §1.3 requires. A package joins only by a change to the list, reviewed as a change to the origin's trusted code, never because a listed package, Pret UI or boxel-ui included, starts depending on it; the base realm, the host and `runtime-common` are never on it. `tests/import-allowlist.test.ts` pins what is refused. A stylesheet's `@import` and `url()` are inlined rather than bundled as modules, so the package's stylesheets may not `@import`, and a `url()` may name only a relative path inside the package (boxel-ui's typeface, served beside the stylesheet at run time, is one).
- **`session.js` is an entry of its own**, so it is served whole with its exports under their own names: the matrix suite's `secure-window.spec.ts` imports it from the origin and calls it as the window does.
- **CSS.** Components style themselves as the host's do (ADR 019 §1.4): `<style scoped>`, compiled by `glimmer-scoped-css` into the build's stylesheet files, over boxel-ui's CSS variables and in `rem`. A scoped rule is scoped by a `data-scopedcss-…` attribute, not a `style` attribute, so it holds under the policy. `src/styles/layers.css` orders the cascade layers as the app does: boxel-ui's (`vendor`, `reset`, `utilities`, `boxelComponentL1` to `L4`), then Pret UI's `PretComponent` and `PretComposite` above them. The build links it ahead of every other stylesheet (`build/layer-order.ts`), and fails on a stylesheet that names a layer it doesn't order.
- **TypeScript.** The package's own code is `.ts` and `.gts`, in erasable syntax, so Node runs its scripts and tests directly (ADR 019 §1.10). `pnpm lint:types` (`build/type-check.ts`) type-checks it, with Pret UI's real types: it fails on any diagnostic in a file of the package, and passes over those inside Pret UI's and boxel-ui's source, which are written for the host's TypeScript settings and checked by those packages' own lints.
- **The build record.** `build-record.json`, committed, lists each file the entry documents load (the probe's under `probe/`), its size, and each module in it by package, version and size. A module from another package in this repository (Pret UI, boxel-ui, boxel-icons) also carries a `sha256` of the file the build reads for it: its source, or for boxel-icons its built file, with the `moduleName` paths its build bakes in cut back to `packages/` so the hash is the same in every checkout. `pnpm build` rewrites the record. `pnpm lint:build`, part of the package's lint in CI, rebuilds and fails when the output differs from it, and when such a hash moved the failure names those modules and ADR 019 first. So a bump to Ember, to any allowed package, or a change to a Pret UI, boxel-ui or boxel-icons module the origin ships shows, in its pull request, exactly what changes on the origin. Template module names are written from the package root, or from the repository's root for other packages' modules (`build/relative-module-names.ts`), and the build fails if any chunk still names the checkout it was built in. Commit the record with the change that moves it.
- **The policy holds for the build.** No template binds or sets `style` (the template lint's `no-inline-styles` with `allowDynamicStyles: false`). `pnpm lint:pretui` (`build/pret-ui-lint.ts`) applies the same rule to every Pret UI module the package imports, and every Pret UI module those import, and also refuses a `<style>` element left unscoped, one created at run time and a `style` attribute set at run time. The policy test catches a `style` attribute anywhere a page renders one, boxel-ui's included. Code that styles an element at run time uses the CSSOM (`element.style.setProperty`). A Pret UI component that paints from a per-instance value (Spinner's size, Alert's and Badge's tone, Chip's and Token's hue, LoadingState's pixel delays, the field metrics of Input, Textarea and PasswordInput, Meter's bars) writes it with Pret UI's `keepStyle` modifier (`internal/keep-style.gts`) and binds no `style` of its own; boxel-ui writes with `setCssVar`, as LoadingIndicator does. A dropdown's list renders in the wormhole, outside its component, and its rules still go in the component's scoped style, never an unscoped `<style>`. BoxelSelect names the list through `:global()`. A Pret UI module can't: the realm compiles Pret UI for cards with `:global()` refused (`noGlobal` in `runtime-common/transpile.ts`), so Pret UI Select renders a hidden marker inside the list that gives the list the marker's scope attribute, and styles it with plain scoped rules and `:deep()`. The shell's document holds the wormhole (`#ember-basic-dropdown-wormhole`, after `main`), and `global.css` carries `ember-basic-dropdown`'s positioning rules in the `vendor` layer, as boxel-ui's `global.css` brings them to the app. Entry documents hold no inline script or style. The pages are never served from a Vite dev server, which injects styles inline.
- **Serving.** The build writes asset URLs under the placeholder base `/__SECURE_ORIGIN_BASE__/`, and `dist/manifest.json` maps each entry document to the files it loads. `createSecureOrigin` reads the manifest and the files once, at startup, and replaces the base with the shell's path. A realm server configured with a secure origin refuses to start without a build. Nothing is built at request time.
- **Where it is built.** Before every process that serves the origin starts. The realm-server image (`realm-server.Dockerfile`) builds it once, after building boxel-icons' JS in a stage of its own that stays cached until boxel-icons, the root `package.json`, or the dependency fetch's inputs (the lockfile, `pnpm-workspace.yaml`, `.pnpmfile.cjs`, `patches/`) change. The build writes `dist/inputs.json`: a hash of every file it read, of the `package.json` of each package those files belong to, of the `tsconfig.json` each file compiles under and every config it extends, of the files that configure it, and of every file it wrote. The deployed start scripts (`scripts/start-staging.sh`, `scripts/start-production.sh`) run `pnpm build:secure-origin:if-stale`, which serves the image's build when every one of those files still matches, and builds again when the build or its record is missing or a file differs. `pnpm lint:build` fails when a fresh build's record wouldn't be accepted. So a container normally starts without building, inside ECS's health-check grace period, and one whose image build doesn't match its sources still gets a fresh one. The dev and host test stacks (`mise-tasks/services/realm-server`), the realm-server and boxel-cli integration suites (their `run-*-with-test-pg.sh`) and the matrix suite's global setup build it every time. `pnpm build:secure-origin` in `packages/realm-server` builds it by hand.
- **CI.** The Lint job runs the package's lint (the allowlist, the record, `lint:pretui`, the type check) and its unit tests. The Secure Origin Tests job restores boxel-icons' build and runs the component tests. CI's cache of that build (`.github/actions/restore-icons-cache`) is keyed on the inputs the image's boxel-icons stage and `build/ensure-icons.ts` rebuild on: boxel-icons' own sources, the root `package.json` and the dependency fetch's inputs. So the build CI checks the record against is the one the image ships. Both, and the realm server's suite with the policy test, run on a change to `packages/pretui`, `packages/boxel-ui` or `packages/boxel-icons` as well as to the package (ADR 019 §1.8).

## The key pages

The secure window's key pages are where a person keeps their keys: adds one, replaces or deletes it, shares one into a realm, or shares one in place of a shared key that stopped working. Each runs inside `KeysWindow` (`src/shell/keys/keys-window.gts`): the sign-in page's purple (`--auth-page-background`, named in `global.css`) behind a bar with the logo and a Close button, and the page in a white panel laid out as a card's edit format (`edit-page.gts`: a muted header band, then one labelled row per field, each with its icon).

- **No sign-in of its own.** A key page never signs in, as it never signs out (ADR 005 §1.6). Its session is the one Boxel's own sign-in on this origin leaves here. Without one, or once it ends while the window is open (the app's sign-out ends the window's sessions on the server, or another window on this origin forgets or replaces the stored session), the page says to sign in to Boxel from the page that opened it and shows nothing else. It notices from a `storage` event, from `GET /_secure-session` when the window comes back into view or focus, and from any request refused as signed out.
- **The pages.** `keys` (also the shell's own address) lists the user's keys as a linksToMany field lists cards: a tile per key saying which services it is used with (the realm server's registrable domains, from the key's grants) and listing each workspace it is shared with ("Shared with N workspaces"), by name and address with the labels its shares there go by, each with Unshare (`key-use.gts`), and under it each active share no operation is approved to send (`approvedCalls` 0) saying "Not approved for any calls yet" with Approve for a card, then Share with Workspace and Replace, a delete button beside it, and Add a key under them. All of it comes with the key listing (`usedWith`, `sharedInto`; see the `user-keys` skill), so the page asks nothing per key. A workspace the user can no longer read comes without a name and is shown by its address. Unshare asks first, then deletes the key's shares in that workspace (`DELETE /_key-shares/:id`, the owner's own, no ticket), and the key stays shared everywhere else. Delete lists the shares it would suspend and can't be confirmed until that list loads. `enter-key` is the one page a key's value is typed into. Opened for an operation, it offers only the kinds of key the operation's `userKey` slots take, from the context's per-slot `kinds` (the card's declared `keyKind`, or `slotKeyKinds`; see the `call-api` skill): one kind is a Kind row saying what the card needs, with no choice, and several are a narrowed choice starting on the first. A connected account is made on `connect`, never entered here, so an operation that takes only that replaces the page with `connect` for the same card and operation, and one that takes it among others offers "Connected account (OAuth)", whose action is Connect an account. The approve page likewise offers a slot only the keys and shares that can fill it in every operation of the batch: of a kind each operation's slot takes (`BatchSlot.kinds`, falling back to its declared `keyKind`), and good at every destination the slot is sent to (`serves` on the batch's keys and shares, which for an OAuth key is its client's API hosts) (`slotChoices` in `approval-batch.ts`). Switching "When calls run" changes which operations, and so which keys, the batch shows, and a key no longer offered gives way to the one the slot starts on. `share-key` shares an existing key into a realm: from Share with Workspace on a key (`keys/<key id>/share`) it asks which workspace, in `WorkspacePicker` (`shell/keys/workspace-picker.gts`, which the use-with-card page shares): Pret UI's Select with its search (`@searchEnabled`), over the realms `GET /_secure-window/realms` lists, each named, with its address after the name where another has the same name (`workspaceOptions` in `shell/keys/workspaces.ts`, through Select's option `meta`); with none, the page's own message says why in place of the Select; opened for a realm (`#realm=<realm>`) it asks which of the user's keys. The page reflects the realm's policy and offers no choice of its own about people who aren't signed in (`share-key-page.gts`; see the `key-shares` skill). Where the context's `realm.opensToAnonymous` is false, it is the signed-in-only page ("**Only signed-in people** with access to this workspace can use it. People who aren’t signed in can’t."). Where it is true, sharing a key there means people who aren't signed in will use it. If the chosen key allows anonymous use, the intro bolds "and so will people who aren’t signed in", and a read-only row says the key allows it (with its anonymous caps, a day and a month) and that sharing it here means they will use it. If the key doesn't, Share key is disabled, and the page says the key can't be shared here and links to the key's page to allow it first; the realm server refuses such a share too. Sharing never changes the key's setting and posts no anonymous attributes. Whether a key allows anonymous use is set, for a key that can serve visitors (not a sign-in app or a connection, which get no Change on the key page), when adding it (the add-key page's "People who aren't signed in" checkbox, with the same optional daily and monthly caps, `anonymous-use-fields.gts`, worded by `anonymous-caps.ts`) or later from the key's page (`PUT /_user-keys/:id/anonymous-use`; see the `user-keys` skill). `swap-key` shares one of the user's keys in place of a suspended share. It follows the same rule as `share-key`: in a realm whose `realm.opensToAnonymous` is true it says in bold that people who aren't signed in "will use this key", and a key that doesn't allow anonymous use is refused there (the realm server answers 400). `replace-key` is opened for an operation: it asks the context with `bindings: true`, which says for each of the operation's credential slots what the user's binding (or the realm's share) fills it with and whether the service rejected that key's grant. It offers the replace form for the user's own key, or a key they share; when any slot is rejected, only the rejected keys. One of the user's OAuth connections is signed in again rather than replaced, so for one it offers Reconnect, which opens `connect` with `#reconnect=<key id>` as the key page's Reconnect does; a connection counts as rejected when its service refused to refresh it, as well as when its grant is rejected. For someone else's shared key it says who can replace it. The context names a share's label only to its owner and the realm's direct writers, and its owner only to those writers while the share is active (the `key-shares` visibility rules). Adding a key and sharing one are separate changes: the share and swap pages never take a key's value, and with no keys they point to the key page.
- **How the app opens a key page.** Cards, the app and the AI assistant all open one through the same host tool, `open-secure-window` (`packages/host/app/tools/open-secure-window.ts`; a card reaches it through `@context.toolContext`). It takes a mode (`enter-key`, `replace-key`, `share-key`, `swap-key`, `connect`, `approve` or `review-changes`; `replace-key`, `approve` and `review-changes` need an operation, and the last two name only the one a card is blocked on, never its others), what the key is for (a card and operation, a card type's module, export and realm and operation, for a share the realm, for a swap the realm and the suspended share) and a one-line reason, and opens `<mode>#<those>` (`secureWindowURL` in the host's `lib/secure-window.ts`) as a popup. It answers only `opened` or `blocked`, never anything the user did. It opens the popup with an opener, so that a blocked popup can be told apart (a `noopener` open answers null either way), cuts the popup's `opener` at once, and keeps no handle; the opener policy below severs the windows as the page loads. That keeps the secure page from reaching the app page. It doesn't keep card code, which runs in the app page, from opening a window of its own or replacing `window.open`: against card code, the defence is the secure origin itself, the one address bar a key is typed under. A blocked popup puts up `SecureWindowFallback` (mounted for operator and host mode alike), whose "Open the secure window" button opens the same address on the user's click and names the address bar to check. It shows nothing the caller wrote, since any card can raise it; the window shows the reason, labelled as the opener's. The assistant's system prompt (`SYSTEM_MESSAGE` in `runtime-common/ai/constants.ts`) tells it to call the tool once when an operation is refused "Binding not approved" naming a credential slot "for the invoking user's own key" (the wording `describeSlots` in `card-operations/call-api.ts` gives the refusal, since the code and `meta.slots` don't reach the model; a stored key doesn't fill the slot, so it never reopens the window on a repeated refusal) and to open `replace-key` once, with the card and operation, when an operation is refused "Credential rejected", and never to ask for a credential in the chat; the `missing-key-opens-secure-window` evaluation in `packages/ai-assistant-evals` checks it.
- **Connect mode.** `connect` signs the user in at a vendor through an OAuth client, making a connection (see the `oauth-connections` skill). Opened for an operation (`#card=…&operation=…` or `#module=…`), for a realm (`#realm=…`), to reconnect one of the user's connections (`#reconnect=<key id>`, from its Reconnect button on the key page) or bare (Connect an account on the key page), it lists the clients `GET /_oauth/clients` offers for the realm and the operation's destination — Boxel's, the realm's shared ones and the user's own — each with the host it signs in at and the permissions (scopes) it asks for. Connect mints a ticket (`add`, or `replace` of the connection being reconnected), posts `POST /_oauth/connections`, and sends the window to the vendor's authorization URL the server answers with. The vendor sends the person back to the realm server, never to a page here, and the realm server sends the window on to `connected` with the one-use `#code=…&state=…` (or `#error=<code>`), which the page reads, takes out of the address bar, and finishes with the window's own session (`POST /_oauth/connections/complete`). A sign-in `boxel keys connect` started also carries `cli_port` and `cli_state`: the page then needs no session and finishes nothing, but asks the user to **Continue in the terminal** and posts the code and state (or the error) to the CLI's loopback listener with `handToCli`, and the CLI finishes the sign-in with its own secure session. No token reaches either page. The add-a-key page also adds an OAuth app (client id and secret, its grant, endpoints, scopes and API hosts), and says that GitHub needs a GitHub App rather than an OAuth App. A connection's tile on the key page shows its client and whether it needs reconnecting or an administrator, and offers neither Replace nor Share: a connection is its owner's own sign-in.

One choice per slot covers the batch, keys whose grants cover it first, preselected when one fits; "Add a new key" goes to `enter-key` with `then=approve` (or `review-changes`), which comes back with the new key chosen. A slot the user's own key fills and one a key they share with the workspace fills are never drawn alike. Each is a section of its own, a tinted Pret UI Card (`shell/keys/key-audience.gts`) headed by a large icon in a disc, what kind of key it is, and whom it serves, following "When calls run": the user's own key is a neutral section, "Only you", which approved for open cards serves the card's scheduled calls and the user's own use of it (everyone else who uses the card chooses a key of their own); a share approved for open cards is an info-toned section, "Everyone in <workspace>", against the share's limits, or a warning-toned "Anyone, signed in or not" where the realm's policy and the share's key let people who aren't signed in make the calls; a share approved for the schedule only is "The card’s schedule in <workspace>", which opening the card doesn't use and which counts against no limits. A shared key replaces any share chosen for those calls before. Each tile carries its kind's icon, and a share's tile names the key it shares. The intro and the done page say the same, the done page naming each share by its label. The use page (`keys/<key id>/use`) draws the key or share it sets up in the same section, without a use, which is chosen next, and the share and swap pages draw the key being shared in the shared-key section, with a line of their own (`@line`); the swap page heads it "Shared in <workspace>" (`@headline`), since the key goes into the share, which keeps its label and its approvals, whichever calls those are. The section is named by its two heading lines, and the radio group inside it by the same two. A connected account it sends on to `connect` comes back the same way: just before leaving for the service, `connect` keeps the approve page's fragment in the window's session storage beside the sign-in's `state`, and `connected` takes it back once and returns there with the new connection chosen, only for a sign-in it finished with that `state`; a sign-in that failed offers Back to the approval instead (`shell/keys/approval-return.ts`). A connect started for no approval forgets any kept before. While an approval `boxel keys approve` opened is on `enter-key`, `connect` or `connected`, closing the window still cancels it. A chosen key with no grant where a group sends is a new grant: that group says so by its full host, never the label, and the Approve button is the one confirmation, with a line beside it summing up each host a key goes to for the first time. Unticking an operation leaves it out, and a key the service rejected is marked and never preselected. Checkboxes are Pret UI's Checkbox, radio buttons Pret UI's RadioGroup (through `RadioChoices` in `shell/keys/radio-choices.gts`), and the keys, apps and cards to choose between Pret UI's RadioCard. Each draws every state itself (`appearance: none`), never left to the browser, which under the shell's dark color scheme paints an unchosen radio as a dark disc on the white panel; a RadioCard keeps its real radio in the tab order, so the arrow keys move the choice. The key window themes them (`KeysWindow`'s panel): `--pretui-control-border` (the muted foreground) edges an unchosen box or radio, `--pretui-control-checked-border`, `--pretui-radio-checked-fill` and `--pretui-choice-card-tone` (the primary ink) a chosen one's edge, a chosen radio's fill under its white dot and a chosen tile's ring, and `--ring` (the primary ink) every focus ring, each 3:1 or more on the white panel where the theme's teal and input edge are too faint. Each row of a key page is a horizontal Pret UI Field with its icon (`@orientation='horizontal'`, `@icon`) that keeps no line for a message (`@reserveMessage={{false}}`), since its control shows its own errors; a row whose content is a group or a value shown rather than a control takes `@labelTag='span'` and names its group with the label's id. Opening a key's usage and limits, and a grant's approvals, is Pret UI's Disclosure. "When calls run" offers "On a schedule and when the card is opened" first and starts on it, except where every request in the batch was last approved for pipelines only, or `boxel keys approve` opened the page without `--interactive` (`initialUse` in `approval-batch.ts`). One `POST /_key-bindings` approves the rest; a 409 reloads the batch, keeping what the user ticked and chose. Opened by `boxel keys approve` (`#…&operations=<name>,…&cli_port=…&cli_state=…`, read by `cliOpenedFor` in `opened-for.ts`), only the named operations start ticked, and once approved (or when there was nothing to approve) the page posts `window_outcome=done` to the CLI's loopback listener with `handToCli` instead of closing. Before that, its Cancel button, or the window's Close in any state (signed out and load failed included), posts `window_outcome=cancelled` instead, so the terminal stops waiting at once. `KeysWindow` does the posting (its `@cli` argument, `api.tellCliDone()` and `api.close`), once per window. A close while a page's change is saving (`api.saving`) waits for it to settle, so a change that lands is told `done` and only one that didn't is told `cancelled`, and `enter-key` reached from such a page with `then=approve` carries the same listener. `swap-key` does the same for `boxel keys swap`. Closing the browser's own window or tab tells the CLI nothing: a closing page can't start the navigation that reaches the listener, and `connect-src` names no loopback address, so the CLI waits out its `--timeout`. The hand-off carries nothing else: the CLI reads what changed from the realm server, whichever outcome came. `review-changes` asks with `review: true`. Use with a card on a key's tile (`keys/<key id>/use`) asks for a workspace (`GET /_secure-window/realms?access=read`) and a card there (`POST /_secure-window/cards`), then opens `approve` for that type with `#key=<id>&then=keys`, which starts on that key and goes back to the key page. Opened for one of the key's shares (`keys/<key id>/use#realm=…&share=…`, from Approve for a card on the key page or on the share's `share-limits` page, which says the same of a share with no `operations`), the workspace is the share's, the cards are those sending the realm's key from a slot no share fills yet (`attributes.slot: 'apiKey'`; a slot another share fills stays with it), and `approve` opens with `#share=<id>&then=keys`, starting each `apiKey` slot on that share with only the operations that send the realm's key ticked. The done page then says the card can make its calls "on its schedule and whenever anyone opens it, **including people who aren’t signed in**, without asking you again."

A row's label icon is the plain key (Key, Key in use, a connection), since the row's content says whose key it is. The key sections' discs draw the person or the group, the group marks "Shared with" on the key page, and people who aren't signed in are always the incognito figure (boxel-icons `hat-glasses`), the amber section's disc included, never the group.

- **What a change says it does.** Replace says how many workspaces the key is shared with, and Delete says it's permanent. A Google service account's tile shows its email, the user it acts as and its scopes (`service-account-details.gts`, from the listing's `serviceAccount`), and its Replace starts _Act as_ and _Scopes_ from them, so a replace that leaves them alone keeps them; the key file is always chosen anew. `replace-key` does the same from `GET /_user-keys/:id` (the context's bound key is only `{id, name, kind}`), once that read settles and only while neither field has been typed in; when the key has no details it says the replace sets all three anew. A chosen file for another service account than the key's says so beside the fields, since delegation and scopes are granted per service account. `ServiceAccountFields` draws those notes for both pages from its `@replacing` argument. A key saved from a page opened for a card says the card will ask before it can use the key, and the needs-admin page says that someone with direct write access to the workspace needs to set it up. The pages say "direct write access", never "edits": write access from a `*` or `users` row, or a permission policy that admits a write, doesn't make someone a direct writer.
- **What a page is opened for rides in the fragment**: `#realm=…&share=…`, `#key=…`, `#card=…&operation=…`, or `#module=…&name=…&realm=…&operation=…`, with an optional `reason=` (`src/shell/keys/opened-for.ts`). A realm, card or module is a URL or a prefix-form id. These only name things. The page asks the realm server what they are with `POST /_secure-window/context` (`packages/realm-server/lib/secure-window.ts`), under the window's own session, and shows what it answers: the realm's name and whether the user is a direct writer of it, the card definition's display name, and the operation's label, method and destination. Only the reason is shown as given, under "Why it’s needed", attributed to the operation that opened the window ("Given by <operation label> when it opened this window", or to the card when there is no operation), with control characters and invisible format characters (bidi controls among them) taken out, except the two joiners, so emoji sequences and shaped scripts survive. A realm is shown with its address as well as its name, since anyone can name a realm anything. The route resolves identifiers only through the VirtualNetwork, decides realm membership with `RealmPaths`, and answers only when the user may read the realm named, the realm holding the card, and the realm holding the card's or type's module; anything else is a 404 alike with a realm that doesn't exist.
- **A destination** is shown by its registrable domain in large type, then what the request does there in plain words (`methodPhrase`: "Reads from" for GET, "Sends data to", "Deletes at"), its full host and path, then the card and realm, by name and address, it comes from (`destination.gts`), under "This request sends it to". The realm server computes the registrable domain (`registrableDomain`, with `tldts` and private suffixes included, so `alice.github.io` is its own); the page never derives one, and an operation's label never stands in for the host.
- **Every change takes its own ticket**, minted with the window's session just before the request it is for (`src/security/keys.ts`): `add`, `replace` or `delete` of one key, `share` of one key into one realm, `swap` of one key into one share.
- **Only a direct writer shares or swaps.** For anyone else `share-key` and `swap-key` say "An administrator of this realm needs to set this up" and offer nothing to type.
- **A load that fails** for anything but an ended session keeps the page's title and shows the error as the app does (`components/error-display.gts`, a port of the host's ErrorDisplay): a general message, with the HTTP status and the server's own message, or that no response came, behind Show Details. It offers Try again only when that could go differently: no response, a 5xx, a 408 or a 429. A 404 says the workspace, card or request doesn't exist or the user can't read it (the server answers 404 for both), a 403 says the user doesn't have access, and a link that names nothing the page can show throws `LinkError` (`shell/keys/context.ts`) and reads as a 404. None of those offer Try again.
- **Done, the window closes** (`navigation.close()`) when it was opened for something. A window the user opened themselves can't be closed by script and stays on the page saying what was done. A page reached from the key page goes back to it instead. The app learns the outcome by asking the realm server, never from the window.

## The credential fields the app frames

Every input in the app that a password is typed into — the profile modal's change password, and the change-email modal's "confirm your identity" — is a cross-origin frame of `credentials#form=<form>&origin=<app origin>`. Unlike the secure window, the frame is meant to be invisible: the user sees the app's own form.

- **What the frame is told rides in the fragment, never the query.** A WAF rule in front of staging refuses any query string that contains `localhost` or `127.0.0.1`, so `?origin=http://localhost:4200` would be a 403 and a blank frame for every local host. The fragment is never sent to the server, so no filter sees it, and the load balancer's access log never records it. A page that isn't on the user's own machine passes them in the query as well (`credentialFieldsURL` in the host's `lib/credential-fields.ts`), and the frame reads the query when the fragment names no form, so a host bundle that sends only the query and a realm server that reads only the query each still work with the other side. Anything else the app or the CLI hands the secure origin that names an origin or a URL goes in the fragment or another channel that isn't the query, for the same reason.

- **Where a password goes is the realm server's, not the app's.** `createSecureOrigin` writes the Matrix server's URL (the realm server's `--matrixURL`) and the realm server's own (`serverURL`) into the page's markup, and names those two origins alone in `connect-src`. The frame sends every request carrying a password to the Matrix server, itself, but for `set-password`, which it sends to the realm server: the realm server sets the password on the Matrix server and then ends the account's secure sessions (the `secure-session` skill). Nothing the app sends can change either destination, so card code driving the frame can't redirect a password.
- **Framed by the app's origins alone.** `frame-ancestors` names `--serverURL`'s origin plus each `--secureOriginAppOrigin` (the host dev server and the test runner in development; the staging host PR previews' `https://*.boxel-host-preview.stack.cards` on staging; and on staging and production alike, a host app on the developer's own machine: `https://localhost:*`, `https://127.0.0.1:*` and their `http:` twins). No remote page can have a loopback origin, so those admit only a page served from the user's own machine: any such page, on any port, not only the host app. Production lists nothing else: a password manager fills a saved production password into the fields wherever they are framed, so a branch preview, a Railway deployment or a custom domain is added to staging's list by name, never production's. An origin whose host starts with `*.` stands for every subdomain of the rest, and one whose port is `*` for every port of its host, in `frame-ancestors` and in the frame's own check (`isListedOrigin`) alike. The realm server normalizes each configured origin with `appOrigin`, which refuses anything that isn't a single origin of that shape. The same list is written into the page, and the frame talks only to a parent on one of those origins, checking each message's origin and that it comes from its parent window. The host checks the frame's messages with `isTrustedMessageOrigin` and the frame's window.
- **What crosses the boundary.** The app sends what isn't secret: theme values, a username, an interactive-auth dict without its password, its own access token (change password, change email), and "make this request". The frame sends back whether each field is filled in and valid (never what is in it), its height, and the Matrix server's response — which for sign-in is the session the app already keeps. Before it goes, a response is checked for any password typed into the frame.
- **Card code can still drive the frame.** It runs in the app page, so it can send the frame the same messages the app does, and the frame can't tell the two apart. It can't read a password or change where one goes, but it can choose the non-secret parts of a request the user's password then authorizes — for example, the email verification session `add-threepid` binds. Keep every parameter the app sends to what a request can't do harm with, and fix in `credentials.js`, or in the realm server that a request goes through, anything that decides what a password authorizes (as the realm server fixes `logout_devices: true` for `set-password`).
- **Forms and requests are fixed in `credentials.js`.** Each form names its fields and the one request it may make; a request names its Matrix endpoint and the body it sends, taking from the app only the parts that aren't secret. A new form or field is added there and in the host's `CredentialForm` type, never by the app passing field definitions.
- **The protocol is a plain module; the fields are components.** `src/security/credentials.js` holds the frame's whole conversation with the app as a `CredentialFrame`: what each field holds, validation, the `state` and `size` it reports, the requests and their redaction. It renders nothing and is handed everything it reaches (the parent window, `postMessage`, `fetch`), so it is tested without a page. `src/credentials/` draws the fields from it (`credential-fields.gts`) and mounts them (`main.ts`) only when `mayStart` allows.
- **It looks like the app because the app styles it.** The fields are drawn with Pret UI's Field and Input, and AuthFormField (`src/components/`). The settings modal's are horizontal Fields whose label column is the app's `--boxel-field-label-size`, and every Field's label takes the app's `--boxel-label-*` type, so they line up with the app's own FieldContainers. The form sets Pret UI's field knobs to the app's control height (`--boxel-form-control-height`, which the host also reserves the frame's height by before the fields report theirs) and to the page's type size (`1em`). Every `var(--…)` in those styles is resolved by the host component at the frame's position and sent over, and written onto the frame's document through the CSSOM (`src/credentials/style.ts`), so a theme or token change reaches the frame. The fields render under a booted, empty application instance (`src/credentials/main.ts`): boxel-ui's input draws its element with a classic component, which needs an owner. A layout that follows the space around it (the settings modal) sets `--credential-layout: narrow`.
- **A flow that re-sends the password keeps the frame mounted.** Registration and change-email retry their requests across several screens, so their forms stay mounted, hidden, until the flow ends. Unmounting the frame forgets the password.

## How a page talks to the realm server and the Matrix server

A page reads what it shows from the realm server, and sends what is typed there, never from or to the page that opened it. It does this with `fetch` to the realm server's own origin, cross-origin. The secure origin never serves realm-server endpoints itself: that would be the passthrough forbidden above.

Creating an account and asking for a reset email are Matrix requests the page makes itself (`matrix.js`): registration's user-interactive auth (the invite code where the Matrix server asks for one, and the email validation it polls for), and the email validation links. Setting the new password goes through the realm server (`changePassword` in `session.js`), which makes the Matrix request and then ends the account's secure sessions. The shell's policy names exactly two origins besides its own in `connect-src`, the realm server's (`serverURL`) and the Matrix server's (`--matrixURL`), both from the realm server's configuration and both written into the page's markup, never a wildcard. The endpoints a page calls answer CORS for the secure origin.

An email link that lands on a page carries anything secret in its fragment, never its query string, because a load balancer's access log records query strings: `reset-password`'s client secret is in the fragment, with the email address the link was sent to, and the Matrix server appends the validation session's id after them. The page reads them and takes them out of the address bar.

Submissions go through `fetch`, not a `<form action>`, so `form-action 'self'` stays as it is, but for the CLI's loopback hand-off.

- **Everything else is a 404**, on any method, with the same headers. A non-GET to the shell is a 405.

## Headers on every response

`secureOriginHeaders()` sets them, error responses included:

- `Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. There is no `unsafe-inline` and no `unsafe-eval`.
- `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`, `Cache-Control: no-store`.
- `Cross-Origin-Opener-Policy: same-origin`. The page that opens a secure window keeps a handle to it. Same-origin policy stops that page reading the window, but not navigating it, so card code could swap the window for a look-alike partway through a flow. This policy cuts the handle: the opener sees the window as closed. It also cuts `postMessage` to the opener, which no page uses. The app learns an outcome by asking the realm server again.
- No CORS headers: the gate runs before the realm-server's CORS middleware.

**Framing is per document, never per page.** Every page is the shell's one response, so relaxing framing on the shell would relax it for every page, the key-entry window included. A document the app frames, such as the password forms, gets a path of its own and its own entry in `routes`. That entry's `headers` pass the app's origins in `frameAncestors`, which puts those origins in `frame-ancestors` and drops `X-Frame-Options`, since that header can't name an origin. An app origin may be a `*.` subdomain pattern the realm server is configured with, such as the staging host previews, or a `:*` port pattern, such as the loopback origins. Never pass a bare `*` or a scheme alone, and never relax the shell's route or the defaults.

## How requests reach it

- **Deployed:** the hostname has its own load balancer, which forwards everything on that host to the realm-server, keeping the `Host` header. `scripts/start-production.sh` and `scripts/start-staging.sh` pass `--secureOriginURL` (`https://secure.boxel.ai/`, `https://secure.stack.cards/`). Without that flag the realm-server treats the host like any other and serves the full app on it. A realm-server started anywhere the secure hostname reaches must carry the flag. `secureOriginGate` is the first middleware in `RealmServer#buildApp`. A request whose `Host` (or `:authority`) is the secure origin's host is answered there and never reaches CORS, request logging, the routes table or a realm. Keep it first.
- **Development:** `--securePort` opens a listener of its own (`RealmServer#listenSecureOrigin`) that serves only the secure origin, whatever `Host` it is sent. The listener is 4208 (`SECURE_PORT` and `SECURE_ORIGIN_URL` in `mise-tasks/lib/env-vars.sh`), on the dev realm-server that both `mise run dev` and the host test stack start. It is a different origin from the app (`localhost:4200`) and from the realm-server (`localhost:4201`), so isolation is real without DNS. In branch mode it is registered with Traefik as `realm-server-secure.<slug>.localhost`.
- The host reads the URL from `secureOriginURL` in its config: `SECURE_ORIGIN_URL` at build time, set for deployments in `packages/host/config/{staging,production}.env`.

The secure origin must never share a host with the realm-server, the host app or a published realm. Port 4201 would not do: it serves realm content and the host app.

## What is never recorded

- **Request logging** for the origin is its own: one `secure-origin <METHOD> <path>: <status>` line per request (logger `realm:secure-origin`). It records no query string, no headers and no body, because a ticket or a credential can travel in any of them. The realm-server's `realm:requests` logger never sees these requests. The `aws-access` skill shows how to find these lines and the load balancer's access logs in a deployed environment.
- **The load balancer's access log does record the query string.** So a ticket or anything secret travels in a request body, or in the URL fragment, which never leaves the browser. It never travels in the query string.
- **Sentry** records the body of any incoming request a handler reads. `scrubSecureOriginEvent` (installed in `instrument.ts` as `beforeSend` and `beforeSendTransaction`) reduces an event raised during a secure-origin request to its method and URL path. A host is covered once it is registered, which `createSecureOrigin` does.
- An error while answering is logged by message and turned into a 500 there and then. It is never rethrown to the app's error handler, which would report the request to Sentry.

## Its client telemetry

The shell beacons what its pages do to the realm server's `/_client-telemetry`, as the host does, each batch naming `client_app: 'secure-origin'` ([ADR 014](../../../docs/adr/014-beacon-the-secure-origins-telemetry-to-the-realm-server-and-let-no-secret-into-it.md)). `shell.js` starts the instrument (`src/shell/telemetry.ts` over `src/telemetry/instrument.ts`) before the app boots; the credential fields never start it.

- **What it records.** `server-request` for every call a page makes, by an endpoint label; `page-load` for each page opened (its label, time to first render and, for a key page, until its data loaded, and whether the load ended `loaded`, `load-failed` with the failed call's label and status, `signed-out`, or `left`); `client-error` for an uncaught throw or rejection, with the page; `wedge` when the main thread froze for 10s or more, corroborated by long-animation-frame or longtask entries spanning at least half of it so a wake from sleep isn't one, and attributed to the scripts that blocked it; and a `keepalive` while quiet. It flushes every second, and everything at once on `pagehide`, when the window is hidden, and in `navigation.close()` before the window closes.
- **How a call is timed.** `timedFetch` in `src/security/session.js` makes every request `session.js` and `matrix.js` send. Once the instrument observes it, a realm-server request also carries `X-Boxel-Logging-Correlation-Id`, which joins it to the server's `realm:requests` line; a Matrix request never does, as Synapse's CORS doesn't allow the header.
- **How a page reports.** The router reports each page opened and rendered (`app.gts`). `KeysWindow` takes its page's visit (`pageAwaitsData()`) and reports a window with no session through it; each key page calls `api.visit.loaded()` once its data is in and `api.visit.loadFailed(e)` where it shows `LoadFailed`. A visit reports only its own page, so a load that ends after the user moved on reports nothing. A new key page does the same.
- **Who it is attributed to.** The window's own session, as the beacon's bearer token, once it has one; the body names no user. Before that the realm server accepts the beacon, attributes it to nobody, writes it as the secure origin's whatever it claims, and rate limits its events by the sender's network.
- **Nothing sensitive goes in it, by construction.** A request is recorded only as an endpoint label from the fixed list in `src/telemetry/labels.ts`, its method, status, timing and size; its URL, query and bodies are never read, nor any header but the response's `Content-Length`, which gives its size. A path segment that can carry an id is matched as `:id`. A page is named by its label, never its address or fragment. An error's message is scrubbed (`scrubMessage`): a refused request becomes its status and code, never the server's words, and anything quoted, any URL and any Matrix ID or email address becomes `*`; the stack keeps only its frames. A wedge names a blocking script by its URL's origin and path (`scriptURL`: none unless the path is a script file's, so never the page's own address) and its function name, and what invoked it only by its type, never the invoker, which can be an element's id or a URL with its query. **A new call needs its shape added to `labels.ts`**, or it reports as `other`, and a new page needs its route in `PAGES` there. Never add a field that carries a value a page shows or a user typed. `tests/integration/telemetry-test.gts` drives the key pages with known secrets and fails if any beacon carries one, and the sign-in, registration and password-reset tests run the instrument through every flow they drive and fail if a beacon carries anything typed or sent (`tests/helpers/telemetry-secrets.ts`). A test of a new page does the same.
