# ADR 020 remediation

Places where the code does not meet [ADR 020](../020-run-every-launched-browser-with-its-sandbox-on-and-a-current-chrome.md)
yet (ADR 001 §1.6).

`packages/runtime-common/chrome-sandbox.ts`:

- `chromeSandboxEnabled` breaks §1.2. It turns the sandbox off on every Linux
  host, though the reasons its comment gives hold only on some of them:
  Playwright's bundled Chromium on a host that blocks unprivileged user
  namespaces, and Chrome running as root. Whether the sandbox starts on CI's
  runners or in the prerenderer's ECS task has not been tested. The launches
  below take their Linux gate from it.

These launches break §1.2 on Linux, through `chromeSandboxEnabled`. On macOS
and Windows they keep the sandbox on, except for the prerenderer's V8 `--prof`
diagnostic, which §1.2 allows:

- `packages/realm-server/prerender/browser-manager.ts` (`BrowserManager.getBrowser`).
  The deployed prerenderer runs here. Its image runs as the non-root
  `pptruser` and installs `google-chrome-stable`, which ships the setuid
  sandbox helper, so neither reason holds in that task.
- `packages/realm-test-harness/src/support-services.ts` (`launchStandbyBrowser`)
- `packages/realm-server/scripts/wait-for-host-standby.ts` (`main`)
- `packages/realm-server/tests/secure-origin-policy-test.ts` (the `before`
  hook's `puppeteer.launch`)
- `packages/boxel-cli/src/lib/test-engine.ts` (`runQunitInBrowser`)
- `packages/software-factory/src/screenshot-execution.ts` (`captureHtmlScreenshot`)
- `packages/software-factory/playwright.config.ts`
- `packages/software-factory/playwright.realm.config.ts`
- `packages/matrix/playwright.config.ts`
- `packages/ai-assistant-evals/playwright.config.ts`
- `packages/choreo-gallery/scripts/record-tutorial.mjs`
- `packages/choreo-gallery/scripts/verify-tutorials.mjs`
- `packages/choreo-gallery/tools/check-published-site.mjs`

`packages/realm-server/tests/secure-origin-policy-test.ts`:

- the `before` hook's `puppeteer.launch` breaks §1.5 with
  `--disable-features=IsolateOrigins,site-per-process`. Its comment names the
  behaviour it needs (the framed credential fields in the page's own process)
  but not why no narrower flag gives it.

These testem configs break §1.2: each adds `--no-sandbox` whenever `CI` is set,
with Ember's template comment "needed when running Chrome inside a container",
or no comment, as the only reason:

- `packages/host/testem.js`
- `packages/host/testem-live.js`
- `packages/realm-server/testem.js`
- `packages/boxel-ui/testem.cjs`
- `packages/boxel-ui/docs-app/testem.js`
- `packages/secure-origin/testem.cjs`
- `packages/choreo/testem.cjs`
- `packages/glimmer-motion/testem.cjs`
- `packages/choreo-film-app/testem.js`

These launches break §1.5: each relaxes certificate validation for the whole
session without gating it on a loopback origin:

- `packages/ai-assistant-evals/playwright.config.ts` (`--ignore-certificate-errors`
  and `ignoreHTTPSErrors`, while `EVAL_HOST_URL` can name any host)
- `packages/ai-assistant-evals/assistant-eval.spec.ts` (`ignoreHTTPSErrors` on
  its own context)
- `packages/matrix/playwright.config.ts` (`--ignore-certificate-errors` and
  `ignoreHTTPSErrors`, for `localhost` and for `published.realm`, which the
  same launch maps to loopback, but with no gate on either)
- `packages/matrix/tests/secure-window-keys.spec.ts` (`ignoreHTTPSErrors` on
  its own context)
- `packages/host/testem.js`
- `packages/host/testem-live.js`
