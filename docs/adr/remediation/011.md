# ADR 011 remediation

Places where the code does not meet [ADR 011](../011-reveal-a-users-matrix-id-only-to-users-who-share-a-realm-with-them.md)
yet (ADR 001 §1.6).

- The homeserver configurations for staging and production are kept outside
  this repository, so no entry here can name them. They break §1.6 until each
  one sets the user directory, profile and invite settings that the templates
  under `packages/matrix/support/synapse/` set, and loads
  `boxel_invite_check.BoxelInviteCheck` under `modules:` with the
  `realm_server_url` of its realm server and a `shared_secret` equal to that
  realm server's `MATRIX_INVITE_CHECK_SECRET`.
  `.github/workflows/sync-synapse-assets.yml` copies
  `packages/matrix/support/synapse/modules/` to those homeservers, but each
  configuration still has to list the module.
- `packages/matrix/support/synapse/modules/boxel_invite_check.py` and
  `packages/realm-server/handlers/handle-invite-check.ts` tell service users
  from end users by the naming convention `isBotAccount` applies, which
  registration doesn't reserve. A person who registers a name that matches
  it holds an end user's account that both treat as a service user's, so
  that account may invite, or be invited by, an end user it shares no realm
  with. That breaks §1.5 and §1.6. The module still keeps two accounts it
  takes for end users out of one room unless they share a realm.

§1.8 has no gaps. The operations it governs
(`packages/runtime-common/card-operations/read-history.ts`) do not exist, and
the `realm-policy-authoring` skill is kept in the boxel-skills plugin, outside
this repository; the sentence §1.8 requires of it is owed when the operations
land.
